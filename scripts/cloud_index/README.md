# Cloud-backed GrepMesh text index

Status: 4 direct-source-tree scopes on server-100 index Agent Herder, ExManager, video_watching and the explicitly selected Omniroute code/test subtrees (41,176 corpus records after deployment) in Yandex.Disk, alongside 896 older pilot documents on server-44. Combined total: 42,072 scope entries, not necessarily distinct files. This is NOT full fleet migration.
Results: [initial pilot](../../benchmarks/cloud-index/2026-10-31-real-yadisk.md), [legacy OCR / unified cloud index](../../benchmarks/cloud-index/2026-10-31-legacy-ocr-and-path-index.md), [compact FTS5 / Airlock canary](../../benchmarks/cloud-index/2026-10-31-compact-fts-airlock.md), and [video_watching / parallel cold reads](../../benchmarks/cloud-index/2026-10-31-video-cloud-parallel.md), and [Omniroute code-only cloud scope](../../benchmarks/cloud-index/2026-10-31-omniroute-code.md).
No native fleet index was deleted, switched off, or replaced. The cloud-backed pilot is limited to its declared text policy; full-text queries via the main GrepMesh still require authorized filesystem ACL propagation.

## Storage contract

- Source scanner reads original UTF-8 text/code files directly: Git-tracked files for the Git scanner, or currently present tracked/untracked eligible files for the tree scanner. It does not read or build a local search SQLite index.
- Publisher builds bounded immutable SQLite shards in tmpfs. A contentless FTS5 trigram table uses `detail=none,columnsize=0`; compressed body text is stored once per distinct body within a shard. Queries use bounded conjunctions of safe individual trigrams with exact-body verification. Short/tokenizer-unfriendly queries fall back to a bounded per-shard scan, never an authoritative empty response.
- A compact path-only SQLite index is also written per scope and preloaded into bounded RAM, so filename globs do not require fetching all full-text shards.
- Durable shard objects and immutable generation manifests live in the configured private cloud prefix. The latest pointer is published only after the full source footer and object verification succeed.
- Reader loads requested shards into a byte-bounded LRU in tmpfs. Default index cache cap is 512 MiB; each raw shard is at most 64 MiB. Full-text reads prefetch only up to six candidate compressed shards concurrently, preserving manifest order; validation, SQLite access, and LRU mutations remain on the owning request thread. Compressed-transfer buffers, manifests, SQLite caches, and the interpreter are additional RAM, so a service cgroup is still required.
- Runtime refuses non-tmpfs paths. It never silently spills its index/cache to an SSD. The existing authenticated rclone gateway is used without reading or copying credentials. Its optional scratch/cache are explicitly placed in RAM as well.
- Source-scoped generations make changed, renamed and deleted tracked text files visible after a reader manifest refresh/restart. Old cloud manifests and objects remain available for rollback. Automatic cloud garbage collection is intentionally not implemented yet.
- A missing footer, changed source file, missing input file, permission failure, corrupted object or query deadline must not become an authoritative empty result.

## Current supported scope

One explicitly admitted Git working tree or narrow current-source tree per corpus (with optional top-directory selection), plus an optional **one-time legacy extraction bootstrap** from the already existing read-only GrepMesh FTS/OCR database for a separately admitted narrow source root. The latter preserves existing extracted PDF/DOCX text but is NOT a replacement for fresh PDF/OCR extraction after cutover. Multiple scopes can be exposed through one `multi_cloud.py` peer; the shared RAM-cache budget is bounded.
Supported extracted UTF-8 bodies are at most 1 MiB each. Symlinks, known secret filenames, binary/unsupported formats are excluded and reported by source policy. A completed policy scope does not imply the full native 81 GiB index is migrated.

Historical bodies **above** that 1 MiB limit are no longer unread: `oversize_support.py` publishes them as newline-aligned content-addressed chunk objects (`oversize/<host>/<snapshot>/<body_sha>/chunk-NNNN.zlib`) with one per-snapshot manifest and pointer, and `multi_cloud.py` serves them lazily. A scope config entry `"oversize": {"host":…, "snapshot":…}` attaches an oversize index to a scope; on a `read_text` route miss the reader consults it (paths stay scoped to that scope's admitted source root, loaded lazily, chunk-verified by digest, same fail-closed ACLs, same response shape, same 1 MiB response guard and deadline handling, honest corrupt/missing/timeout errors, no change to hash routing and no fan-out across scopes). Search over oversized bodies is supported with the same shared deadline and honest `partial`/`truncated` reporting. This is a historical read/search parity path, verified against `body.splitlines()` reference line numbering across chunk-cut boundaries (including `\r\n`, U+2028/U+0085 and mid-piece cuts).

Literal/case-insensitive text and path retrieval, filename glob search and a **bounded-regex text search** (`mode=regex`) are implemented. Regex latency is bounded: a sound required-literal extraction from the parse tree routes shards by trigram Bloom filters (a missing required literal verifies against no shard), and every matching call carries the remaining deadline through the optional hard-timeout engine; deadline stops are reported honestly as `partial=true` with a warning, invalid regexes fail with an explicit error instead of empty results. Relevance ranking remains unimplemented. The **isolated, unregistered server-44 historical review** now has a narrowly tested `read_text` MCP method for the archived 849,721 searchable documents (path hash-routing, SHA-256 body verification, bounded line ranges, fail-closed ACL root filtering). A live private Yandex.Disk read matched the indexed body SHA-256, including negative forwarded/forged ACL checks. This is **snapshot recovery**, not a live-source `read_text` parity claim: it excludes the 75 oversized cold-only archive texts, and true verified GPTAdmin filesystem ACL propagation and production MCP consumer cutover remain untested. The production installed multi-scope reader and native indices were not switched. The worker listens only on loopback and requires an existing authenticated connector/SSH path. Forwarded text queries require a filesystem read ACL and its roots filter results; this does not replace the transport's authentication. **A filesystem ACL is never trusted from tool arguments.** `forwarded_acl_roots` refuses any request whose arguments carry a `filesystem_acl`, and a forwarded read (`hop_count >= 1`) is admitted only when the policy arrives over an authenticated transport: the authorized relay signs the exact request body plus the policy bytes with HMAC-SHA256 (`GREPMESH_CLOUD_ACL_SECRET`, headers `X-GrepMesh-Filesystem-Acl` and `X-GrepMesh-Acl-Signature`). Without a configured secret no forwarded read is admitted, a forged signature, a modified body, a swapped policy and a signature replayed for other arguments are all refused, and a verified policy can only narrow the readable corpus. `test_cloud_acl.py` proves each of these cases.

The new reader must be deployed before publishing `detail=none` shards; older phrase-MATCH readers cannot query that format. A per-shard trigram Bloom filter can avoid unnecessary fetches. Its false positives only cause extra reads. Bloom size is fixed; very large or broad corpora may need improved routing/filters. Cold searches across many uncached shards can be much slower than warm searches; measured real-cloud latency applies only to the narrow pilots, not millions of documents.

## Configuration boundaries

GREPMESH_CLOUD_GATEWAY names the already authorized SSH/rclone gateway; the reserved value `local` uses the existing authenticated `rclone` executable directly on the same host (server-100), skipping a redundant SSH hop. The remote SSH gateway remains the transport on server-44. Both modes enforce a tmpfs scratch directory, and neither copies tokens or weakens filesystem ACLs. GREPMESH_CLOUD_RCLONE selects the installed executable. Both source identity and source root must be explicitly supplied. No credentials belong in this repository.

Application data and caches belong in /run/user/<uid>/grepmesh-cloud-index. Ordinary program source/configuration on disk is small and is not the search database.

Repository resource rules still apply: explicit cgroups, no concurrent heavy rebuild, bounded memory and CPU. The standalone module also applies process affinity. A source scan is not a promise that the entire filesystem has been covered.

## Tests and rollout gate

The test_cloud_index.py harness uses synthetic files and an in-memory cloud transport, with all temporary SQLite files in tmpfs. It covers source-body search, Cyrillic and expanding case-folding, cache misses/hits/eviction, empty-cache recovery, source/root restrictions, read-ACL filtering, source changes/deletions/renames, incomplete publication, corruption, case-distinct paths, contentless FTS, source-agent exclusions, and bounded regex: sound literal routing (no cloud fetch when the required literal is absent), per-line anchor semantics with `^`/`$`, inline case flags, cross-line `(?s)` and literal `\n` matches, invalid-regex explicit errors, federated-scope regex, a hard-deadline cap on pathological backtracking, and end-to-end regex over the loopback MCP JSONRPC envelope. `test_publish_native_oversize.py` covers oversize chunk publishing with MemoryStore (federated scope tests live in `test_multi_cloud.py`): full-body and random-range line parity for multiple chunk targets and exotic terminators, idempotent re-publication, chunk/manifest tampering and integrity checks, fail-closed ACLs, `deadline`/`byte guard` and accounting behavior. `test_cloud_acl.py` covers the fail-closed ACL transport: fabricated ACL in arguments refused, forwarded read without an authenticated policy refused, HMAC-signed policy accepted, policy narrowing honoured, forged signature / modified body / swapped policy / signature replay refused, local read unchanged.

Before removing any native fleet database:

1. Inventory/allowlist every native source root and format; preserve already extracted OCR and attachments as needed without exporting secrets.
2. Publish each complete scope, fetch it from an empty cache, and measure cold/warm query latency and actual cache/cgroup memory.
3. Implement source-side updates/OCR without the old SQLite; preserve native coverage and formats, source changes/deletions, caller authorization, and complete/partial response semantics.
4. Verify the existing federated peer with authorized full-text reads (the current ACL gate must be preserved, not bypassed), not just path discovery.
5. Only then stop the old writer and remove the old index after checking that it contains no unique irreplaceable extracted content.

The code contains no native-database deletion command. The existing 81 GiB server-100 index remains unchanged by this work.

## Full historical-data archival (separate from live search)

`export_native_archive.py` creates an immutable, complete private cloud archive of the **original FTS document bodies**, deleted-path history still present in the legacy database, extracted OCR cache, row-ID mappings, pending OCR/attempt metadata, and SQLite metadata. It reads the source in a single consistent SQLite WAL snapshot, uploads independently checksum-verified compressed JSONL chunks directly from memory, and publishes `archives/<host>/<snapshot>/complete.json` **only after every table and the manifest are verified**. This is a lossless *logical source archive*, not a working native FTS index or a new full-text search service. FTS token structures can be reconstructed from the source bodies and preserved row IDs. It neither deletes local SQLite nor claims full online search parity.

Run under an explicit bounded cgroup with `GREPMESH_CLOUD_GATEWAY`, `GREPMESH_CLOUD_RCLONE` and a tmpfs `--root`. Each read pins a consistent WAL snapshot; the command **aborts if the source WAL exceeds 3 GiB** so live write amplification cannot silently fill SSD. An interrupted archive has no completion pointer and is not accepted for deletion. A completed backup still needs restoration verification and an authorized full-search cutover before the native database can be removed. See `test_export_native_archive.py` for a synthetic round-trip including deleted source paths and OCR.

`verify_native_archive.py --host server-44 --snapshot <snapshot-id> --validate-json` rereads every archived cloud object, verifies its SHA-256, logical-row checksums, ordering, schema and exact record counts. `recover_native_archive.py --host ... --snapshot ... --path <original-absolute-path> --sha-only` retrieves one historical body by its preserved path/FTS row ID without needing the original file, and returns only digests by default. These tools read through the authenticated private cloud gateway and do not expand the main GrepMesh MCP privileges. Cold recovery is not a substitute for a complete, low-latency full-text search service.

`reindex_native_archive.py` can generate eight disjoint, source-host-bound **private, unexposed** full-text cloud scopes from a completed archive. Each corpus can be published with two independent bounded workers into immutable cloud shards, retaining all tmpfs staged streams until every scope has finished; `--reuse-staged` revalidates the complete source footers before trying a new publish. Historical-only imports explicitly request a 16 MiB text shard threshold, while normal project scopes continue using their 8 MiB default. A private experimental importer may raise the per-shard document flush count to 8192 to reduce remote uploads, without changing the installed production reader or its 64 MiB raw-shard cap. It stages compressed source bodies only in tmpfs, partitions by stable path hash, preserves documents for which no current source file exists, records oversized/unadmitted historical bodies, and never switches native search or changes a production MCP registration. Search parity, ACLs and ongoing updates must be verified before admitting these scopes to the default mesh; restoring files by path and creating FTS shards is not yet a complete indexer cutover. `verify_reindexed_archive.py` validates private fulltext manifests against exact archived document count and excluded oversized rows before any private preview. The dedicated `grepmesh-cloud-legacy44-review.service` is **disabled by default**, listens only on loopback port 19438 and must not be attached to a broad/unauthenticated GPT Admin profile. Starting it after all eight manifests pass is a non-destructive canary, not a switch of fleet search consumers.

Historical cloud search in the private review: glob/path queries run against hot path-only indexes concurrently; **full-text scope queries use one shared wall-clock deadline and stop once the requested hit limit is filled**, with `truncated=true` if additional scopes were not searched. This avoids multiplying remote `rclone cat` requests across eight buckets and never falsely reports a deadline-exhausted search as complete. On 2026-11-01, an authenticated local preview query for `grepmesh` in `/home/roomhacker` returned five hits in **6.64 seconds** (`partial=false, truncated=true`), versus 55.61 seconds for the original full eight-scope serial traversal and a timeout when all eight were prefetched concurrently. These numbers are point-in-time observations, not all-query latency guarantees.

## Server-100 provisional archive with bounded WAL

The production native server-100 SQLite has over 3 million indexed paths and remains actively writable. A single export transaction caused WAL growth to about 718 MiB after only ~50,000 FTS texts, so it was cancelled without publishing any completion pointer. Creating a separate SQLite snapshot was not permitted by the connected execution environment; that boundary must not be bypassed.

`export_native_rolling.py` is an **alternative provisional capture**, not a SQLite snapshot: it reads batches of at most 128 rows with independent short-lived read transactions, writes immutable SHA-256 checked gzip chunks directly to private Yandex.Disk and checkpoints a resumable `progress.json`. Every checkpoint explicitly declares `consistent_snapshot=false` and `safe_for_deletion=false`. The source SQLite is never edited. A locked tmpfs control file prevents competing exports, and the process aborts if the source WAL exceeds 2 GiB. Starting a new unique snapshot requires `--create`; continuation requires its existing cloud checkpoint. Synthetic tests cover interruption/resume, exact row order/contents and a refused duplicate archive ID.

A completed, independently verified rolling checkpoint may be followed by an
**optional high-row-ID catch-up** using export_native_rolling.py with --create,
--lower-rowid (the parent checkpoint's upper row ID), --base-snapshot (that
completed parent's ID) and a new unique --snapshot ID. Supply the **same**
offset/base flags on resume. It captures only FTS text rows whose row IDs
exceed the preceding checkpoint's recorded upper bound, with an immutable
parent reference, independently checked chunks, a shared nonblocking exporter
lock and the same bounded short reads/WAL threshold. The verifier refuses a
delta whose parent or source does not match, whose row IDs overlap, or whose
deletion-safety flags are relaxed. **This is a provisional high-rowid capture,
not a change journal or consistent snapshot:** updates/deletions at older row
IDs, transient rows lost between checkpoints, OCR/extraction metadata, and
the writer-freeze reconcile remain uncovered. Never combine these checkpoints
into a deletion-authorizing receipt.

**Never delete or redirect the original 81.1 GiB SQLite based on this provisional archive.** A separate frozen-writer reconciliation, complete OCR/extraction metadata capture, verified full-text search and authorized consumer cutover are still required.


## Scheduled current-source snapshot refresh (deployed on server-100)

The `refresh_git.py` script refreshes only explicitly allowlisted Git or source-tree projects from server-100, without reading its legacy SQLite index. It verifies the complete source stream and original cloud manifest. If unchanged it performs zero writes. If changed, it publishes a new immutable generation with the pointer written last, while retaining the previous version for rollback. Empty scans, malformed data, or sudden loss of over half the documents fail closed. Runtime source streams and SQLite shards must remain in tmpfs.

This is a bounded full-scope refresh, **not incremental per-file indexing**. It supports at most 100,000 documents and 256 MiB of source-stream data per scope (64 MiB default for nonproduction use). PDF/OCR extraction refresh is not implemented. The active timer `grepmesh-cloud-projects-refresh.timer` runs every 30 minutes under a user-systemd cgroup, with a 512 MiB RAM-cached search service. See `refresh_tree_scopes.example.json` and `systemd/` for the deployed Agent Herder, ExManager, video_watching and code-only Omniroute policy; `refresh_git_scopes.example.json` remains available for the two Git pilots. An unchanged scope performs zero cloud writes. Any changed scope is published atomically and triggers the cloud search service to restart and reload its verified manifests. The scheduled refresher and manual publisher share a nonblocking `publisher.lock` in tmpfs: overlapping runs fail closed, and failed scans release the lock without changing the active cloud pointer. User authorization alone does not grant a GPT Admin connection the verified filesystem ACL required by native multi-peer full-text routing.
